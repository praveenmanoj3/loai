Project idea

We're building a web-based AI video tool that can turn videos into short-form vertical content.

The long-term product is:

A collection of AI-powered video tools where the user's own computer performs the heavy processing instead of our servers.

The first tool is:

Video → Shorts

Eventually:

YouTube URL → automatically find good moments → create vertical Shorts → generate captions → export

The product should be designed around local processing wherever technically practical.

2. The core business idea

The business model is:

The biggest advantage is infrastructure cost.

We do not want to operate GPU servers for video processing.

The user's hardware does the expensive work.

3. VERY IMPORTANT PRIVACY PRINCIPLE

The product should eventually be able to say:

"Your video is processed on your device."

But only display stronger claims such as:

"Your videos never leave your device"

when we have actually verified that the entire workflow doesn't send the video anywhere.

We don't want marketing claims that aren't technically true.

The preferred architecture is:

Video
 ↓
User device
 ↓
Processing
 ↓
Result

rather than:

Video
 ↓
Our server
 ↓
Our GPU
 ↓
Result
4. Why we're avoiding a server GPU

Traditional architecture:

10,000 users
     ↓
Our servers
     ↓
GPU processing
     ↓
Huge infrastructure cost

Our architecture:

10,000 users
 ↓    ↓    ↓
GPU  GPU  GPU
 ↓    ↓    ↓
USER USER USER

The website should therefore be mostly responsible for:

UI
configuration
orchestration
model delivery
processing logic
displaying results

rather than performing the heavy processing on our infrastructure.

5. Browser-first architecture

The primary experience should be browser-based.

Users should ideally be able to:

Open the website.
Upload a video.
Click Generate.
Wait while their device processes it.
Download the result.

They should not need to download an .exe just to try the product.

This is important for trust.

6. Optional local executable later

For extremely heavy processing, we may eventually provide:

Local Processing Engine

Architecture:

Website
   ↓
Optional local engine
   ↓
User CPU/GPU
   ↓
Processing

But this is not the primary Week 1 experience.

If we eventually introduce it, it should be:

Clearly branded
Open-source where practical
Explain exactly what it does
Require minimal permissions
Provide a GitHub repository
Ideally digitally signed
Provide checksums/releases
Clearly explain why it's necessary

Never make users download a suspicious-looking executable without context.

16. The most important engineering rule
DO NOT build unnecessary backend infrastructure.

Before adding:

Node backend
Database
Cloud GPU
Storage
Authentication

ask:

"Does this actually need to exist if processing happens locally?"

If not, don't add it.

The initial product should ideally be deployable as a mostly static web application.
